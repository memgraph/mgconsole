A · Collapse the Meta-command dispatch onto one decision

Was: Strong Verdict: demoted → thin dedupe · shipped

The "collapse" doesn't survive the deletion test. A shared CommandIntent is a near-1:1 relabel of MetaCommand: it removes neither dispatcher's match. Its only load-bearing content is the policy it carries — strip that out and it's a pass-through (delete it, nothing concentrates). The sync-vs-async execution split is mandated by ADR 0010 (the non-blocking Workbench emits Effects; QueryRunner is synchronous), so it cannot move behind a shared seam.

What was real: the read-only-off message had already drifted between the two Frontends. Shipped: three pub const operator-message strings in repl.rs (readonly-off, watch-in-tx, connect-aborts), referenced by both dispatchers. Refusal rules stay inline; the two dispatchers stay separate by design. No intent layer, no ADR.

B · Merge the result-layout split into one module

Was: Worth exploring Verdict: rejected

The split tracks real consumer boundaries. The report assumed render_table was internal to display.rs — but core/src/import.rs:170 calls it directly. An import wants a plain table; it has no notion of Display mode (no auto, no vertical fallback).

Deletion test runs backwards: merge tabular into display and the import path must now depend on the Display-mode module just to get a table — worse coupling. The render_records interface is already deep; the "round-trip" is documented, deliberate reuse of the real measurement.

Claimed "how a Display mode renders" bounced across three thin modules with a leaky measure→decide round-trip. In fact the round-trip is documented reuse, and the three modules each have distinct external callers — decomposition, not fragmentation.

C · Concentrate connection-target resolution

Was: Worth exploring Verdict: rejected

Two different problems, not one duplicated. Startup is a per-field precedence merge (explicit < CLI < profile) producing Connection. :connect is profile-name-or-host:port, inheriting the current Session, producing ConnectTarget.

The select vs profiles.get "inconsistency" is justified: --profile is must-be-a-profile (fatal, helpful error); :connect <target> is maybe-a-profile-else-a-host (reportable). The only literal overlap is a ~2-line credentials wrap with different inputs. Shared knowledge already lives in the Profile struct. A unifying resolver would add complexity.

Original hypothesis (superseded)

Claimed a Connection profile resolved two ways with two APIs. The two paths solve genuinely different resolution problems with different output types (Connection vs ConnectTarget) and different argument grammars; the API difference encodes that.

D · Lift the two Frontend drivers out of main.rs

Was: Speculative Verdict: skipped

Locality, not depth — and mis-aimed. The dispatch (run_interactive) is ~120 lines and belongs in main. The real bulk is ~500 lines of REPL production adapters (SessionRunner, RustylineSource, MgHelper) sitting far from the QueryRunner/LineSource seams they satisfy. Relocating them is a navigability tidy with no interface or test change.

The report's "load_queries() doubles FS I/O" was wrong — it's two arms of a match; exactly one runs. Skipped: not architectural, cuts against the review's own finding that the codebase is well-factored.

What shipped

A, demoted: canonicalize the shared Meta-command policy messages

The grilling's net finding: the codebase is well-architected. B and C were rejected as correct factoring (the automated pass couldn't see import.rs using render_table, or the two resolvers solving different problems); D is locality-only. The single real issue was one drifted operator string.

Shipped: three pub const strings in repl.rs (readonly-off, watch-in-tx, connect-aborts), referenced by both dispatchers — the previously-divergent read-only message is now identical across Frontends. Pure hygiene, no behaviour change; 442 lib tests green, clippy + lean clean. No intent layer, no new module, no ADR.
